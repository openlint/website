summary: |
  The seventh OpenLint office hours agreed to start version 2 of the specification alongside version 1, and asked for the project's structure to be written down before it gets harder to change.

  **Status.** `openlint@1.2.0` is on npm with everything from [Next Release Considerations (#41)](https://github.com/openlint/openlint/issues/41): the rulesets split into packages ([#42](https://github.com/openlint/openlint/pull/42), Phil Sturgeon) and the opt-in schema cache from SAP's Open Resource Discovery team ([#39](https://github.com/openlint/openlint/pull/39)). The next releases stay on housekeeping. [conformance.openlint.org](https://conformance.openlint.org) now runs the specification's 240 conformance tests against OpenLint, Spectral, vacuum, the IBM OpenAPI Validator and Insomnia, plus interop cases for Redocly. Miguel Quintero cut the first version of the [MCP server (#13)](https://github.com/openlint/openlint/issues/13) in its own repo; it moves into the org once he has admin access.

  **Rulesets and versioning.** Kin will write a blog post and migration guide section on the new ruleset packages: how they work with npm and Git, and what the default ruleset includes. The split changed the default ruleset but shipped as a minor release, so the project needs clear expectations for ruleset versions, separate from toolbox and spec versions. A process for adding new formats and industry rulesets is also needed.

  **Project structure.** Joost Farla asked for written conventions on how the project is organized: what goes in the monorepo, what gets its own repo or subdomain, and how pull requests, approvals and merge rights work. Kin will draft an ops and governance map, starting small, including which tools are core and which are add-ons (the MCP server and the VS Code extension are the first cases), and a weekly visual of the moving parts.

  **Specification version 2.** Dimitri van Hees and Joost are drafting the next version in [discussion #39](https://github.com/orgs/openlint/discussions/39). Version 1 is what came from Spectral; version 2 can take good ideas from vacuum and others, such as rule categories and `howToFix`, and new formats such as RDF, which the Dutch government is waiting for. Joost will add version 2 drafts to the specification site and sort open issues into version 1 and version 2: anything breaking goes to version 2. New properties can start as `x-` extensions. The toolbox will need a matching 2.0 to try them. Kin noted that the spec should still say whether a rule allows deterministic or AI-generated fixes. He'll add one page showing version 1 and version 2 of the spec and the toolbox, with the roadmap for each.

  **Conformance.** Joost pointed out that the spec's CI and the conformance dashboard now both run the conformance tests. The tests stay in the spec as the source of truth, and the runner should be consolidated: the spec's CI checks OpenLint, and the dashboard adds the other tools.

  **Performance.** With #39 merged, the next step is benchmarks on large documents and large rulesets. Kin argued that a ruleset should flag very large OpenAPI documents in favour of modular ones.

  **Maintainers.** Phil leads the toolbox, Joost the spec, and Kin is the administrator. Each tool will get its own lead maintainer, starting with Miguel on the MCP server. Maintainers are expected to communicate when they step away, and every role should have a backup.

  **API Days Paris (1–3 December)** is the official launch. Kin has three talks that include OpenLint and plans three or four press releases: the toolbox, the spec, possibly the MCP server, and European government. Dimitri will give a quote and suggested OpenLint stickers; Kin is considering a modular logo that pairs with each format's logo. Grant proposals are due in December.
