summary: |
  The fourth OpenLint office hours focused on the formal specification and on how OpenLint can help teams distribute their rules.

  **Specification.** Joost Farla's rewrite of the specification as a formal draft, built with Bikeshed, was ready to merge. It includes tooling that compiles the spec and runs its conformance tests against the current implementation. It also records, inline, the many places where behavior was reverse-engineered from Spectral rather than documented, such as multi-document YAML files, where only the first document is linted. The group agreed to merge it as a starting point and work through the open questions as smaller issues and discussions. It's now published at [spec.openlint.org](https://spec.openlint.org).

  **Toolbox.** Phil and Jakub weren't on the call, so the npm release status carries over to next week. Miguel Quintero is working on TypeScript 7 and an [MCP server](https://github.com/openlint/openlint/issues/13): read-only to start, and designed MCP-first rather than generated from an API. Miriam Greis described companies building agent skills that run linting and open pull requests for easy fixes, and the push at Nordic APIs to make existing APIs "AI ready". Kin connected this to the need many enterprises have for distributing, versioning and evolving their rules, beyond Git and an editor plugin.

  **Research and launch.** Rules research shows most teams use the default ruleset unchanged, so OpenLint's defaults matter. Kin is studying the Dutch government's approach as a blueprint, aiming for a formal OpenLint announcement at API Days Paris, alongside its Open Source Europe government track.

  **Funding.** $1,000 is in the Open Collective account, with European Commission grants to pursue now that Open Source Europe is the fiscal host.

  **Also discussed:** using JSON Schema plus OpenLint rules to constrain the inputs and outputs of open AI models, for example FHIR, ISO 20022 and PSD2, as a side experiment. Future calls move an hour earlier.

<p>From my vantage point, using JSON Schema plus Spectral to govern APIs, they work together: JSON Schema is foundational (here's what should go into an API, here's what should come out), and rules work somewhat like overlays on top, adding completion rules with regex, functions and so on. And the rules are domain-based: a core JSON Schema everyone agrees on, and then, per domain, we decorate, overlay and evolve the governance with different sets of rules. This infrastructure around model inputs and outputs is kind of like a gateway to me. A classic API gateway applies JSON Schema to what it pulls in and what it publishes, and it has to be valid. Runtime isn't always the best place to do it, but in some situations it works. The decision-style approach limits tokens and steers the non-determinism towards determinism, but it feels like one casino game. Depending on whether you're in healthcare, and what jurisdiction or country you're in, you might want different schemas and different sets of rules.</p>
