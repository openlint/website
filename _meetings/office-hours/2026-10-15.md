summary: |
  The third OpenLint office hours focused on **setting the table**: the npm package, the specification site, the docs site, and the base rulesets, so teams can switch from Spectral before anything new is added.

  **Meeting format.** To include people with clashing meetings, office hours will alternate weekly between an hour earlier and the usual time. Splitting into spec and tooling calls is on the table for later.

  **Funding.** Open Source Europe accepted OpenLint as fiscal host, so Open Collective can take donations. API Evangelist is putting in $1,000 to start, and Kin will chase European Commission grants. Small payments for well-scoped pieces of work, like the npm release pipeline and the docs site, are the first candidates.

  **Specification.** Joost Farla demoed a [formal specification prototype](https://github.com/orgs/openlint/discussions/13) built with Bikeshed: testable MUST/MAY requirements, each with a conformance target (a ruleset or a linter) and conformance tests, a machine-readable registry, and versioned releases plus a working draft on a spec subdomain. The group agreed to move it into the spec repo on GitHub Pages. The first version documents Spectral's behavior as it is; modularization needs its own discussion before the first release.

  **Toolbox.** Phil Sturgeon aims to publish **0.1.0** (the rename) within days and 0.2.0 by next week, then a fully backwards-compatible **1.0** with a new core ruleset in a month or two; breaking changes wait for 2.0. The release pipeline needs an organization npm token. `npm install openlint` will be the single entry point. Editor support should cover IntelliJ as well as VS Code, ideally through a language server. Miguel Quintero will look at the MCP server and API after the TypeScript 7 work.

  **Research.** Kin shared the [108 provider-published rulesets](https://apis.io/rules/) behind the alias analysis, and research on public GitHub pipelines that run Spectral. Agent skills validation with Markdown is one of the most-requested new features.

<p><a class="ts" href="https://www.youtube.com/watch?v=ZtJjr1HjFPA&amp;t=844s">00:14:04</a><span class="who">Joost Farla:</span> A while back I opened a discussion about principles we need to agree on to make this specification more formal. I believe OpenAPI has a similar approach, where you can find all versions, including the working drafts.</p>

<p>If we look at a released version (fictional for now), the document looks similar to many specifications, including OpenAPI and Arazzo, which I believe use ReSpec, the W3C tool. I used Bikeshed, which gives a similar result and is very flexible, so you can customize anything. I tried to fit the current specification, which comes from the original Spectral documentation, into a more formal structure.</p>

<p>There's a conformance section that explains how the document is written, what rules apply, what conformance means, and how we do modularization in the specification. One important thing: for a linter, some requirements are about the ruleset (what a ruleset document should look like), and a second part has to specify how a linter should behave. It's interesting to see how we fold that into a single specification.</p>

<p>It explains terminology, and it has a section on the ruleset format. All normative content is written as requirements: concrete "must", "must not" or "may" sentences, which are testable. Every requirement, for example "a ruleset must have at least one of these properties", also has tests. You can expand it and see the conformance tests. It's documentation, so it describes what to test rather than running it; that's a separate conformance suite. The rest is examples and prose, basically the same as the current documentation but combined with the normative parts. There are chapters on documents and on linting, with their own requirements, then the functions, each with a description, an example, requirements and tests. The appendices list all requirements, and all conformance tests grouped by requirement. Each test basically says: if this is the input and I do this, I'd expect this. Like a unit test.</p>

<p>Besides the document, there's the schema, as already published. There's also a registry, a machine-readable version of the specification including the tests, which could be handy for a conformance suite or other tooling that needs to read the spec. And there are conformance test files with input data in JSON and YAML. The working draft is basically the same document with a big "working draft" warning, and it can carry issues inline: open questions about a specific part of the spec, pointing to issues or discussions.</p>

<p>This was purely an experiment, to demonstrate and to have a conversation about whether this is the direction we want to take. So I'm very curious: what do you think?</p>
