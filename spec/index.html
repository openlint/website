Specification

A specification and JSON Schema for OpenLint rulesets: the Spectral ruleset format, specified on its own, so rules can be written, validated, shared and run by any tool.

Status: draft. The document describes the format as implemented today, without extension. It isn't a formal specification yet. Everything lives in openlint/spec; this page summarizes it.

  • Read the specification
  • The JSON Schema (draft 2020-12)
  • The reference implementation

What it covers

  • The ruleset object: the root fields, and the rule that a ruleset must contribute something
  • Rules: given path expressions, then and the core functions, severity, formats, message and shorthands
  • extends, aliases and overrides: inheriting, naming path expressions, and adjusting rules per file
  • Custom functions and extension properties
  • Conformance notes: where the format is looser than a clean design would be
  • Versioning and provenance

What it's for

Governing structured documents, not only OpenAPI. A rule selects nodes in a JSON or YAML document and asserts something about them, so the same format works on AsyncAPI, Arazzo, JSON Schema, CI workflows and configuration. Which document types to support is open in discussion #5.

How the specification will be written

Proposed by Joost Farla in discussion #13, and not yet agreed:

  1. BCP 14 keywords. MUST, SHOULD and MAY carry their RFC 2119 meaning only in capitals. Examples are informative.
  2. Defined terms. A glossary of document, ruleset, rule, match, result, linter and the rest.
  3. Exact normative references, especially for JSONPath, regular expressions, JSON Schema and YAML.
  4. One conformance target per requirement: a ruleset or a linter, never both.
  5. A permanent ID for every requirement, never reused.
  6. Conformance tests for every requirement, implemented by the conformance suite.
  7. A defined result model, based on Spectral's JSON output.
  8. Immutable releases at their own URLs on spec.openlint.org, with work in progress at /draft/.

Open questions: conformance classes, the style of requirement IDs, and whether to publish with Respec, Bikeshed or something else.

Validate a ruleset

Any JSON Schema draft 2020-12 validator works:

npx ajv-cli validate --spec=draft2020 \
  -s schema/v1/ruleset.schema.json \
  -d .spectral.yaml

Editor setup is in Using the schema.

Get involved
